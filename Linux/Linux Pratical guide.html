1.1 — "What kernel are we running?" (3 min)

# What Linux version are we on?
uname -r
# e.g., 5.15.0-91-generic
# Explain: 5 = major, 15 = minor, rest = patch/build

uname -a
# Full info — architecture, hostname, kernel version

cat /proc/version
# Even more detail — who compiled this kernel, with what GCC version

1.2 — "Everything is a file — prove it" (10 min)

# Your CPU? It's a file.
cat /proc/cpuinfo
# Walk through: model name, cores, MHz

# Your RAM? It's a file.
cat /proc/meminfo | head -5

# System load? A file.
cat /proc/loadavg

# Even your running processes are files
ls /proc/
# All those numbered directories = running processes (PIDs)

# Let's look inside one
ls /proc/1/
# PID 1 = systemd. Show: cmdline, status, fd/

cat /proc/1/cmdline
# Shows what command started this process

# The "black hole" — /dev/null
echo "this disappears" > /dev/null
cat /dev/null
# Nothing. It eats everything. Used to silence command output.

# Real example: find all .conf files but hide "permission denied" errors
find / -name "*.conf" 2>/dev/null | head -10
# 2>/dev/null redirects stderr (error messages) into the black hole
# Without it, your screen fills with "Permission denied" noise

# Key insight: no special API needed. cat, grep, echo work on HARDWARE info.

1.3 — "Streams — every program has 3 channels" (10 min)

Theory (draw on screen):

                    ┌─────────────┐
  stdin (0)  ──▶   │             │  ──▶  stdout (1)   → normal output
  (keyboard)       │   PROGRAM   │
                   │             │  ──▶  stderr (2)   → error messages
                   └─────────────┘

Every program gets 3 streams automatically:

  • stdin (0) — input (keyboard by default)
  • stdout (1) — normal output (terminal by default)
  • stderr (2) — error messages (also terminal by default)

These are file descriptors — literally numbered files. 0, 1, 2.

# stdout — normal output goes to terminal
echo "hello"
# This writes to file descriptor 1 (stdout)

# stderr — error messages go to terminal too, but on a DIFFERENT channel
ls /nonexistent
# "No such file or directory" comes out on stderr (fd 2), not stdout

# PROVE they are separate channels:
ls /etc/hostname /nonexistent
# You see BOTH: the error (stderr) AND the valid result (stdout)
# They LOOK the same on screen, but they are two different streams

Redirection — sending streams to files:

# Send stdout to a file (> is shorthand for 1>)
echo "hello" > /tmp/out.txt
cat /tmp/out.txt

# Send stderr to a file
ls /nonexistent 2> /tmp/err.txt
cat /tmp/err.txt
# "No such file or directory" went to the file, not your screen

# Send stdout to file, stderr still shows on screen
ls /etc/hostname /nonexistent > /tmp/out.txt
# Error still appears on screen! Only stdout went to the file.
cat /tmp/out.txt
# Just the valid output

# Send BOTH stdout and stderr to the same file
ls /etc/hostname /nonexistent > /tmp/all.txt 2>&1
cat /tmp/all.txt
# BOTH output and error are in the file

# 2>&1 means: "send stream 2 (stderr) to wherever stream 1 (stdout) is going"
# Read it as: "stderr → same place as stdout"

The patterns you'll see everywhere:

# Pattern 1: Silence errors (send stderr to /dev/null)
find / -name "*.conf" 2>/dev/null | head -5
# Errors disappear, only results shown

# Pattern 2: Capture everything to a log file
some_command > /tmp/output.log 2>&1
# Both output AND errors go to the log file
# ORDER MATTERS: 2>&1 must come AFTER > file

# Pattern 3: Silence everything (both stdout and stderr)
some_command > /dev/null 2>&1
# Nothing on screen at all — useful in scripts/cron jobs

# Pattern 4: Pipe only stdout, errors still visible
grep -r "listen" /etc/ 2>/dev/null | head -5
# grep's "permission denied" errors vanish, results pass through the pipe

# REMEMBER: the pipe (|) only passes stdout!
# stderr goes straight to your terminal unless you redirect it first

1.4 — "System calls — how programs talk to the kernel" (7 min)

# Every program asks the kernel for help via system calls
# Let's SEE them happening

strace ls /tmp 2>&1 | head -30
# Walk through:
# execve() = "run this program"
# openat() = "open this file/directory"
# getdents64() = "list directory entries"
# write() = "print to terminal"

# Count them — how many system calls does 'ls' make?
strace -c ls /tmp
# Summary table: calls, errors, time per syscall

# Simple cat
strace cat /etc/hostname 2>&1 | grep -E "open|read|write"
# openat() → read() → write() → close()
# That's ALL cat does: open file, read contents, write to screen

# Key point: YOUR program never touches hardware.
# It ASKS the kernel. The kernel does the work.

2.1 — "The Linux directory tree" (7 min)

# Everything starts at / (root)
ls /

# Visual tree (just 1 level)
tree -L 1 /

# Where do programs live?
which ls

# Hundreds of commands available

# Where are config files?
ls /etc/
# nginx config, ssh config, hostname, everything is here

ls /etc/nginx/        # web server config
cat /etc/hostname     # machine name
cat /etc/os-release   # what distro is this?

# Where are logs?
ls /var/log/
# syslog, auth.log, nginx/ — all logs live under /var/log

# Temporary files
ls /tmp/
# Cleared on reboot — use for scratch data

2.2 — "/proc — the kernel talks to you" (5 min)

# /proc is NOT a real filesystem. It's the kernel exposing live info as files.
# Nothing is stored on disk — it's generated on the fly.

# How long has this system been running?
cat /proc/uptime
# First number = seconds since boot
uptime  # human-readable version

# How many CPUs?
grep -c "processor" /proc/cpuinfo

# What's the system load?
cat /proc/loadavg
# First 3 numbers: load over 1min, 5min, 15min
# If load > number of CPUs, system is overloaded

# How much disk I/O is happening?
cat /proc/diskstats | head -5

2.3 — "Finding things" (8 min)

# Where am I?
pwd

# List with details
ls -lah
# -l = long format, -a = show hidden, -h = human sizes
# Walk through columns: permissions, links, owner, group, size, date, name

# Hidden files (start with .)
ls -la ~/
# .bashrc, .profile, .ssh/ — these are all hidden configs

# Find a file anywhere
find / -name "nginx.conf" 2>/dev/null
# 2>/dev/null = hide "permission denied" errors

# Find files modified in last 10 minutes
touch /tmp/recent-file.txt
find /tmp -type f -mmin -10

# Find large files (>100MB)
find / -type f -size +100M 2>/dev/null

# Search INSIDE files
grep -r "listen" /etc/nginx/
# Finds every line containing "listen" in nginx config files

# Which file contains a specific setting?
grep -rl "root" /etc/nginx/
# -l = just show filenames, not the matching lines

3.1 — "Reading permissions" (7 min)

# Create a playground
mkdir -p /tmp/perms-demo && cd /tmp/perms-demo

# Create some files
echo "hello world" > public.txt
echo "secret stuff" > secret.txt
echo '#!/bin/bash\n echo "I am a script"' > script.sh

# NOTE: The line above was not working for me, so I added -e. It worked fine:
echo -e '#!/bin/bash\n echo "I am a script"' > script.sh

ls -la
# Show the permission string for each:
# -rw-rw-r-- = public.txt
# Explain: - (file type) | rw- (user) | rw- (group) | r-- (others)

# What about directories?
mkdir mydir
ls -la
# drwxrwxr-x = directory, user=rwx, group=rwx, others=r-x
# x on directory = you can cd into it

# System files — look at real examples
ls -la /etc/passwd
# -rw-r--r-- root root → everyone can READ, only root can WRITE

ls -la /etc/shadow
# -rw-r----- root shadow → only root and shadow group can read (passwords!)

ls -la /usr/bin/bash
# -rwxr-xr-x → everyone can execute bash

3.2 — "Changing permissions with chmod" (8 min)

# Our script isn't executable yet
ls -la script.sh
# -rw-rw-r-- → no x

./script.sh
# Permission denied!

# Add execute permission
chmod +x script.sh
ls -la script.sh
# -rwxrwxr-x → now has x

./script.sh
# "I am a script" — works!

# Numeric permissions — the DevOps way
# r=4, w=2, x=1. Add them up per position.

# 755 = rwx r-x r-x (owner full, others read+execute)
chmod 755 script.sh
ls -la script.sh

# 644 = rw- r-- r-- (owner read+write, others read only)
chmod 644 public.txt
ls -la public.txt

# 600 = rw- --- --- (only owner can read/write — SECRETS)
chmod 600 secret.txt
ls -la secret.txt

# Can others read it now?
# (If you have another user, switch to them and try)

# The DANGEROUS one — never do this in production
chmod 777 public.txt
ls -la public.txt
# rwxrwxrwx → EVERYONE can do EVERYTHING. Security nightmare.
chmod 644 public.txt  # fix it back

# Recursive — apply to all files in a directory
mkdir -p webdir && touch webdir/index.html webdir/style.css
chmod -R 644 webdir/
ls -la webdir/

3.3 — "Ownership — who owns what?" (5 min)

# Check who owns files
ls -la /tmp/perms-demo/
# Your username shows as owner and group

# Change owner (need sudo)
sudo chown root:root secret.txt
ls -la secret.txt
# Now root owns it — you can't even read it anymore!

cat secret.txt
# Permission denied (assuming you're not root and it's 600)

sudo cat secret.txt
# Works — sudo gives you root power temporarily

# Give it back
sudo chown $(whoami):$(whoami) secret.txt

# Real-world example: web server files
# nginx runs as www-data user, so web files need:
# sudo chown -R www-data:www-data /var/www/html/

3.4 — "Quick permission gotcha demo" (5 min)

# GOTCHA 1: Directory needs x to enter
mkdir noaccess
chmod 000 noaccess
ls noaccess/       # Permission denied
cd noaccess/       # Permission denied
chmod 755 noaccess # fix

# GOTCHA 2: SSH keys MUST be 600
mkdir -p ~/.ssh
touch ~/.ssh/test_key
chmod 644 ~/.ssh/test_key
# SSH would REFUSE to use this key — too open
# ssh -i ~/.ssh/test_key user@host → "UNPROTECTED PRIVATE KEY FILE" error
chmod 600 ~/.ssh/test_key
# Now SSH accepts it

# GOTCHA 3: You need write on DIRECTORY to delete a file (not the file itself)
mkdir testdir && touch testdir/file.txt
chmod 555 testdir          # remove write from directory
rm testdir/file.txt        # Permission denied! Can't delete.
chmod 755 testdir          # fix
rm testdir/file.txt        # works now

# Clean up
cd /tmp && rm -rf /tmp/perms-demo

4.1 — "Who am I?" (3 min)

# What user am I?
whoami

# Full identity — UID, GID, all groups
id
# uid=1000(san) gid=1000(san) groups=1000(san),27(sudo),998(docker)

# What groups do I belong to?
groups

# Who else is on this system?
cat /etc/passwd
# Walk through the format: username:x:UID:GID:name:home:shell

# How many users?
wc -l /etc/passwd
# Most are system users (services), not humans
# UIDs < 1000 = system users, >= 1000 = human users

# Just human users
awk -F: '$3 >= 1000 {print $1, $3}' /etc/passwd

4.2 — "Creating users and groups" (10 min)

# Create a new user
sudo useradd -m -s /bin/bash alice
# -m = create home directory
# -s = set default shell

# Verify
grep alice /etc/passwd
ls -la /home/alice/

# Set password
sudo passwd alice
# (type a password)

# Create another user
sudo useradd -m -s /bin/bash bob

# Create a group
sudo groupadd developers

# Add users to the group
sudo usermod -aG developers alice
sudo usermod -aG developers bob
# -a = APPEND (without this, it REPLACES all groups — dangerous)
# -G = supplementary group

# Verify
grep developers /etc/group
# developers:x:1002:alice,bob

id alice
# Shows: groups=...,1002(developers)

# Demonstrate group permissions
sudo mkdir /opt/project
sudo chown root:developers /opt/project
sudo chmod 775 /opt/project
ls -la /opt/
# drwxrwxr-x root developers → group can write

# Switch to alice and test
sudo su - alice
whoami        # alice
touch /opt/project/alice-file.txt    # works — alice is in developers
ls -la /opt/project/
exit

# Try with a non-member
sudo useradd -m -s /bin/bash outsider
sudo su - outsider
touch /opt/project/hacker.txt    # Permission denied!
exit

4.3 — "sudo and root" (7 min)

# alice can't use sudo yet
sudo su - alice
sudo apt update
# "alice is not in the sudoers file. This incident will be reported."
exit

# Add alice to sudo group
sudo usermod -aG sudo alice

apt update # it gives error
# NOTE: The sudo group gives Alice the permission to request root powers,
# but it does not run her normal commands with root powers by default.
sudo apt update # it works

# Now alice can sudo
sudo su - alice
sudo whoami    # root
apt update # it gives error
# NOTE: The sudo group gives Alice the permission to request root powers,
# but it does not run her normal commands with root powers by default.
sudo apt update # it works
exit

# Where is sudo configured?
sudo cat /etc/sudoers
# Show: %sudo ALL=(ALL:ALL) ALL
# Meaning: anyone in the "sudo" group can run any command as any user

# See who used sudo recently (audit trail)
sudo grep "sudo" /var/log/auth.log | tail -10

# Switching users
sudo su - alice       # become alice (with alice's environment)
sudo su - bob         # become bob
sudo -i               # become root

# IMPORTANT: in production, root login via SSH is DISABLED

5.1 — "What is a process?" (5 min)

# Every running program is a process with a unique PID
# PID 1 is always the first process (systemd)
ps -p 1 -o pid,comm
# PID 1 = systemd — the mother of all processes

# The process tree — who spawned whom
pstree | head -30
# systemd → sshd → bash → pstree (your current chain!)

# Your current shell's PID
echo $$
# This is your bash process ID

# Your shell's parent
echo $PPID
ps -p $PPID -o pid,comm
# Probably sshd or the terminal emulator

5.2 — "Viewing processes" (8 min)

# List ALL processes
ps aux
# Walk through columns: USER, PID, %CPU, %MEM, VSZ, RSS, STAT, COMMAND

# Key columns:
# USER = who owns this process
# PID = process ID
# %CPU = CPU usage
# %MEM = memory usage
# STAT = state (R=running, S=sleeping, Z=zombie)
# COMMAND = what program is this

# Top CPU consumers
ps aux --sort=-%cpu | head -10 # highest consuming cpu
ps aux --sort=%cpu | head -10 # lowest consuming cpu

# Top memory consumers
ps aux --sort=-%mem | head -10

# Find a specific process
ps aux | grep nginx
# Note: grep itself shows up in results. Fix:
ps aux | grep [n]ginx
# OR use pgrep
pgrep -a nginx

# Live monitoring
top
# Show: press 'P' for CPU sort, 'M' for memory sort, 'k' to kill, 'q' to quit
# (Press q to exit)

# Better version
htop
# Show: colors, tree view (F5), search (F3), kill (F9)
# (Press q to exit)

5.3 — "Process states — alive, sleeping, zombie" (5 min)

# Start a background process
sleep 1000 &
SLEEP_PID=$!
echo "Started sleep with PID: $SLEEP_PID"

# Check its state
ps -p $SLEEP_PID -o pid,stat,comm
# S = sleeping (waiting for time to pass)

# What about a busy process?
yes > /dev/null &
BUSY_PID=$!

ps -p $BUSY_PID -o pid,stat,comm
# R = running (actively using CPU)

kill $BUSY_PID

# Create a zombie! (child finished but parent didn't collect its exit status)
cat << 'EOF' > /tmp/zombie.sh
#!/bin/bash
# Parent creates a child that exits immediately
# Parent then sleeps without waiting for child — child becomes zombie
bash -c "exit 0" &
sleep 60
EOF
chmod +x /tmp/zombie.sh
/tmp/zombie.sh &
ZOMBIE_PARENT=$!

sleep 1
ps aux | grep -E "Z|defunct"
# May see a Z (zombie) state — process finished but not reaped

kill $ZOMBIE_PARENT
kill $SLEEP_PID 2>/dev/null

5.4 — "Killing processes" (7 min)

# Start some processes to kill
sleep 500 &
PID1=$!
sleep 600 &
PID2=$!
sleep 700 &
PID3=$!

# See them
jobs
ps aux | grep sleep

# Graceful kill — SIGTERM (signal 15) — "please stop"
kill $PID1
# Process gets a chance to clean up (close files, save state)

# Force kill — SIGKILL (signal 9) — "die NOW"
kill -9 $PID2
# No cleanup, no mercy. Use as last resort.

# Kill by name
kill $PID3
killall sleep    # kills ALL processes named "sleep"

# Kill all by user (dangerous!)
# pkill -u alice  ← would kill ALL of alice's processes

# Reload signal — SIGHUP (signal 1)
# Many daemons reload config on HUP
sudo kill -HUP $(pgrep -f "nginx: master")
# nginx re-reads config without stopping — zero downtime

# Real scenario: process won't die
sleep 999 &
STUBBORN=$!
kill $STUBBORN      # try nice first
ps -p $STUBBORN     # still there? (sleep responds to TERM, but imagine it doesn't)
kill -9 $STUBBORN   # nuclear option
ps -p $STUBBORN     # gone

5.5 — "Background & foreground" (5 min)

# Run something in foreground — blocks your terminal
ping google.com
# Press Ctrl+C to stop

# Run in background — terminal stays free
ping google.com > /tmp/ping.log &
PING_PID=$!

# See background jobs
jobs
# [1]+  Running   ping google.com > /tmp/ping.log &

# Bring to foreground
fg %1
# Now it's blocking again. Press Ctrl+Z to SUSPEND it.

# It's now stopped
jobs
# [1]+  Stopped   ping google.com

# Resume in background
bg %1
jobs
# [1]+  Running   ...

# Clean up
kill $PING_PID

# nohup — survives terminal close
nohup ping -c 100 google.com > /tmp/nohup-ping.log 2>&1 &
NOHUP_PID=$!
# Even if you close this SSH session, the process keeps running

# Verify
ps -p $NOHUP_PID -o pid,comm
kill $NOHUP_PID

# Key concept:
# & = run in background
# Ctrl+C = kill foreground process
# Ctrl+Z = suspend (pause) foreground process
# fg = bring to foreground
# bg = resume in background
# nohup = survive terminal close

1.1 — "Understanding Network Fundamentals" (15 min)

Theory — The 5 Things Every Machine Needs to Talk on a Network:

┌─────────────────────────────────────────────────────────────────────────────┐
│                    NETWORKING CONCEPTS EXPLAINED                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  1. IP ADDRESS (Internet Protocol Address)                                  │
│  ─────────────────────────────────────────                                  │
│  What: A unique number assigned to your machine on a network.               │
│  Analogy: Your HOUSE ADDRESS — "123 Main Street, Mumbai"                    │
│  Example: 192.168.1.50 (private/local) or 54.23.100.12 (public/internet)   │
│                                                                             │
│  Types:                                                                     │
│  - Private IP: Used INSIDE your network (192.168.x.x, 10.x.x.x, 172.16-31)│
│    → Your laptop on office WiFi gets 192.168.1.50                           │
│    → EC2 instance in VPC gets 10.0.1.25                                     │
│  - Public IP: Used on the INTERNET (visible to the world)                   │
│    → Your office router has one public IP (e.g., 203.100.50.1)              │
│    → EC2 with Elastic IP gets a public IP                                   │
│  - Loopback: 127.0.0.1 = "myself" (never leaves the machine)               │
│                                                                             │
│  IPv4: 32-bit → 4 numbers (0-255) separated by dots → 192.168.1.50        │
│  IPv6: 128-bit → much longer → 2001:0db8:85a3::8a2e:0370:7334             │
│                                                                             │
│  Real-world use:                                                            │
│  - When you deploy to AWS, your EC2 gets a private IP (for internal talk)   │
│    AND optionally a public IP (for internet access)                          │
│  - When you SSH into a server, you connect to its IP                        │
│  - When you configure nginx, you bind it to an IP (or 0.0.0.0 = all IPs)   │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  2. MAC ADDRESS (Media Access Control)                                      │
│  ─────────────────────────────────────                                      │
│  What: A PERMANENT hardware address burned into your network card (NIC).    │
│  Analogy: Your AADHAAR NUMBER — unique, doesn't change, tied to you         │
│  Example: 02:42:ac:11:00:02 (6 pairs of hex digits)                         │
│                                                                             │
│  Key differences from IP:                                                   │
│  - IP can change (DHCP assigns a new one, you move networks)                │
│  - MAC never changes (it's in the hardware)                                 │
│  - IP works across the internet (Layer 3)                                   │
│  - MAC only works within your LOCAL network (Layer 2)                       │
│                                                                             │
│  Real-world use:                                                            │
│  - WiFi MAC filtering (only allow specific devices to connect)              │
│  - DHCP reservations ("always give this laptop IP .50")                     │
│  - Network troubleshooting (ARP table shows IP↔MAC mappings)               │
│  - AWS: each EC2 ENI has a MAC address                                      │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  3. HOSTNAME                                                                │
│  ──────────                                                                 │
│  What: A human-friendly NAME for your machine.                              │
│  Analogy: Your house has an address (IP) but also a NAME ("Villa Sunrise")  │
│  Example: web-server-01, ip-10-0-1-25, jenkins-prod                         │
│                                                                             │
│  Why it matters:                                                            │
│  - Logs show hostname → you know WHICH server had the error                 │
│  - Prometheus/Grafana labels use hostname                                   │
│  - In Kubernetes, pod names are like hostnames                              │
│  - Naming conventions help teams: prod-web-01, staging-db-02               │
│                                                                             │
│  Real-world use:                                                            │
│  - "The alert says prod-web-03 is down" → you know exactly which server    │
│  - In /etc/hosts, you can map hostname → IP for quick access                │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  4. GATEWAY (Default Gateway)                                               │
│  ────────────────────────────                                               │
│  What: The ROUTER that connects your local network to other networks.       │
│  Analogy: The MAIN GATE of your apartment complex. To go anywhere           │
│           outside, you MUST pass through it.                                 │
│  Example: 192.168.1.1 (your home router), 10.0.0.1 (VPC router in AWS)     │
│                                                                             │
│  How it works:                                                              │
│  - Your machine wants to reach google.com (142.250.190.46)                  │
│  - Is 142.250.190.46 on my local network? NO                               │
│  - So send the packet to the gateway → gateway forwards it to the internet  │
│                                                                             │
│  If gateway is down → you can reach LOCAL machines but NOT the internet     │
│                                                                             │
│  Real-world use:                                                            │
│  - "Server can ping other servers in same subnet but can't reach internet"  │
│    → Check gateway! Probably misconfigured or gateway is down               │
│  - AWS VPC: route tables define gateways (Internet Gateway, NAT Gateway)    │
│  - Docker: containers use docker0 bridge as their gateway                   │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  5. DNS SERVER (Domain Name System)                                         │
│  ──────────────────────────────────                                         │
│  What: A server that translates NAMES to IP ADDRESSES.                      │
│  Analogy: The PHONE BOOK / CONTACTS APP on your phone.                      │
│           You search "Mom" → it gives you her number.                       │
│           DNS: you search "google.com" → it gives you 142.250.190.46        │
│  Example: 8.8.8.8 (Google), 1.1.1.1 (Cloudflare), 10.0.0.2 (AWS VPC DNS)  │
│                                                                             │
│  How DNS resolution works (simplified):                                     │
│  1. Browser asks: "What's the IP of docs.google.com?"                       │
│  2. Local cache → checked first (did I ask this recently?)                  │
│  3. /etc/hosts → checked second (any manual overrides?)                     │
│  4. DNS server → sends query to configured nameserver                       │
│  5. If DNS server doesn't know → it asks root → .com → google.com          │
│  6. Answer comes back: 142.250.190.46                                       │
│  7. Cached locally for next time (TTL = how long to remember)               │
│                                                                             │
│  Real-world use:                                                            │
│  - Route 53 (AWS DNS) — manages your domain's DNS records                   │
│  - "Website is down but server is fine" → often a DNS issue                 │
│  - Internal DNS: service discovery (myapp.internal → 10.0.1.50)             │
│  - DNS propagation: why changes take time (TTL hasn't expired)              │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  6. SUBNET MASK                                                             │
│  ─────────────                                                              │
│  What: Defines which part of the IP is the NETWORK and which is the HOST.   │
│  Analogy: In "123 Main Street, Mumbai" — "Mumbai" is the network part       │
│           and "123 Main Street" is the host part.                            │
│  Example: 255.255.255.0 (or /24 in CIDR notation)                           │
│                                                                             │
│  IP: 192.168.1.50, Mask: 255.255.255.0 (/24)                               │
│  Network part: 192.168.1.___  (first 24 bits)                               │
│  Host part:    ___.___.___.50 (last 8 bits = 256 possible hosts)            │
│                                                                             │
│  Real-world use:                                                            │
│  - AWS VPC subnets: /24 gives 256 IPs, /16 gives 65536 IPs                 │
│  - Security groups: allow traffic from 10.0.1.0/24 (entire subnet)          │
│  - "Two servers can't talk" → are they in the same subnet?                  │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  7. PORT                                                                    │
│  ────────                                                                   │
│  What: A number (0-65535) that identifies a SPECIFIC SERVICE on a machine.  │
│  Analogy: IP = apartment building address. Port = flat number.              │
│           Building has one address, but many flats inside.                   │
│  Example: 192.168.1.50:80 = machine .50, service on port 80 (web server)   │
│                                                                             │
│  One server can run MULTIPLE services:                                      │
│  - Port 22  → SSH daemon (remote login)                                     │
│  - Port 80  → nginx (web server)                                            │
│  - Port 443 → nginx (HTTPS)                                                 │
│  - Port 3306→ MySQL (database)                                              │
│  All on the SAME IP, different ports.                                       │
│                                                                             │
│  Real-world use:                                                            │
│  - Security groups: "allow inbound on port 443 from 0.0.0.0/0"             │
│  - Docker port mapping: -p 8080:80 (host 8080 → container 80)              │
│  - "Connection refused on port 5432" → PostgreSQL not running               │
│                                                                             │

1.3 — "DNS — Translating Names to IPs" (8 min)

Theory:

When you type "google.com" in a browser:
1. Your machine asks a DNS server: "What's the IP of google.com?"
2. DNS replies: "It's 142.250.190.46"
3. Your browser connects to 142.250.190.46

Without DNS, you'd need to memorize IP addresses for every website.

DNS resolution order on Linux:
1. /etc/hosts         → Local overrides (checked first!)
2. /etc/resolv.conf   → Lists your DNS servers
3. External DNS       → Queries upstream (8.8.8.8, etc.)

DNS Record Types (commonly asked in interviews):
- A Record      → Maps domain to IPv4 (google.com → 142.250.190.46)
- AAAA Record   → Maps domain to IPv6
- CNAME Record  → Alias (www.google.com → google.com)
- MX Record     → Mail server (where to deliver email)
- NS Record     → Nameserver (who manages this domain's DNS)
- TXT Record    → Text data (used for verification, SPF, DKIM)

Hands-on:

# ┌─────────────────────────────────────────────────────────────┐
# │ COMMAND: cat /etc/resolv.conf                               │
# │ WHEN TO USE: Find out which DNS server your system uses     │
# │ REAL USE CASE: "DNS resolution failing" → check if DNS      │
# │   server is correctly configured. In Docker containers,     │
# │   this file might point to Docker's internal DNS (127.0.0.11)│
# └─────────────────────────────────────────────────────────────┘
cat /etc/resolv.conf
# nameserver 8.8.8.8 = Google's DNS
# nameserver 1.1.1.1 = Cloudflare DNS

# ┌─────────────────────────────────────────────────────────────┐
# │ COMMAND: cat /etc/hosts                                     │
# │ WHEN TO USE: Check/add local DNS overrides                  │
# │ REAL USE CASE:                                              │
# │   - Testing a new server before DNS propagation             │
# │     (add "54.23.1.1 myapp.com" to test without changing DNS)│
# │   - Blocking malicious domains (point them to 127.0.0.1)   │
# │   - Local development (myapp.local → 127.0.0.1)            │
# │   - Kubernetes pods use this for service discovery          │
# └─────────────────────────────────────────────────────────────┘
cat /etc/hosts
# 127.0.0.1 localhost
# You can add entries: 192.168.1.50 myserver.local

# ┌─────────────────────────────────────────────────────────────┐
# │ COMMAND: nslookup                                           │
# │ WHEN TO USE: Quick DNS lookup (works on all OS)             │
# │ REAL USE CASE: "Is the domain resolving correctly?"         │
# │   Simple, available everywhere (even Windows). Good for     │
# │   quick checks. Use dig for detailed troubleshooting.       │
# └─────────────────────────────────────────────────────────────┘

# Shows: the DNS server used + the answer (IP address)

nslookup google.com 8.8.8.8
# Query a specific DNS server (useful to compare results)

# │ COMMAND: dig                                                │

# Look at ANSWER SECTION: google.com → IP

1.4 — "Testing Connectivity" (10 min)

Theory:

Troubleshooting flow (the "3-layer check"):
1. Can I reach the IP?          → ping
2. Is the path clear?           → traceroute
3. Is the specific port open?   → telnet / nc / curl

If ping works but port doesn't → firewall or service down
If ping fails → network/routing issue

         "Can't reach server" — Decision Tree:
         ─────────────────────────────────────
         ping server_ip
              │
         ┌────┴────┐
         │ Works?  │
         ├─YES─────┼─── nc -zv server_ip port
         │         │         │
         │         │    ┌────┴────┐
         │         │    │ Works?  │
         │         │    ├─YES─────┤→ App issue (check logs)
         │         │    └─NO──────┘→ Firewall or service down
         │         │
         └─NO──────┘─── Check: gateway? DNS? routing? firewall?

Hands-on:

# ┌─────────────────────────────────────────────────────────────┐
# │ COMMAND: ping                                               │
# │ WHEN TO USE: First check — "Is this host reachable?"        │
# │ REAL USE CASE:                                              │
# │   - Server health monitoring scripts                        │
# │   - "Can my server reach the database server?"              │
# │   - Checking network latency between two machines           │
# │   - Verifying VPN connectivity                              │
# │   - NOTE: Some servers disable ping (AWS SG must allow ICMP)│
# └─────────────────────────────────────────────────────────────┘
ping -c 4 google.com
# -c 4 = send 4 packets and stop (without -c, it pings forever!)
# Shows: time (latency in ms), packet loss percentage
# 0% packet loss = good. Any loss = network problem.
# time=1ms = fast (local). time=200ms = slow (far away or congested)

# Ping local gateway (first troubleshooting step for internet issues)
ping -c 3 $(ip route | grep default | awk '{print $3}')
# If this fails → your local network is broken (cable/wifi issue)
# If this works but google.com fails → ISP or DNS issue

# ┌─────────────────────────────────────────────────────────────┐
# │ COMMAND: traceroute / tracepath                             │
# │ WHEN TO USE: "WHERE in the path is the problem?"            │
# │ REAL USE CASE:                                              │
# │   - User reports slow website → traceroute shows high       │
# │     latency at hop 5 (ISP issue, not your server)           │
# │   - Verifying traffic routes through expected path          │
# │   - Debugging VPN routing (is traffic going through VPN?)   │
# │   - "Works from office, not from home" → compare paths      │
# └─────────────────────────────────────────────────────────────┘
traceroute google.com
# Shows each hop (router) between you and the destination
# * * * = that router doesn't respond (firewall, not necessarily a problem)
# High ms at a hop = congestion at that point
# Suddenly stops = traffic is blocked at that hop

tracepath google.com
# Similar but doesn't need root. Also shows MTU.

# ┌─────────────────────────────────────────────────────────────┐
# │ COMMAND: curl                                               │
# │ WHEN TO USE: Test HTTP/HTTPS connectivity, APIs, downloads  │
# │ REAL USE CASE:                                              │
# │   - Health check scripts ("is my API returning 200?")       │
# │   - Testing API endpoints from server                       │

┌──────────────────────────────────────────────────────────┐

│ 80   = HTTP (web traffic, unencrypted)                  │
│ 443  = HTTPS (web traffic, encrypted)                   │
│ 53   = DNS                                              │
│ 25   = SMTP (email sending)                             │

Port states:
- LISTEN      = waiting for connections (service is running and ready)
- ESTABLISHED = active connection happening right now
- TIME_WAIT   = connection closing (normal, will disappear in ~60s)
- CLOSE_WAIT  = other side closed, we haven't (possible bug in your app!)
- SYN_SENT    = trying to connect (stuck here = firewall blocking)

Hands-on:

# │ COMMAND: ss -tulnp                                          │
# │ WHEN TO USE: See what ports are open & which process uses them│
# │ REAL USE CASE:                                              │

# │   - "Port already in use" error → find the culprit          │

ss -tulnp

# -u = UDP

# Same flags, same output, different command

2.1 — "Why Vi?" (3 min)

Theory:

Why EVERY DevOps engineer must know Vi:
1. It's on EVERY Linux/Unix server — even minimal containers
2. When SSH'd into a production server at 2 AM, Vi is your only editor
3. nano might not be installed. VS Code isn't available over SSH (usually)
4. Many tools open Vi by default (git commit, crontab -e, visudo)

Vi vs Vim:
- vi  = original (1976), basic
- vim = "Vi IMproved" — syntax highlighting, undo levels, plugins
- They behave the same for basic editing. Learn vim.

The KEY concept: Vi has MODES
┌────────────────────────────────────────────────────┐
│                                                    │
│  NORMAL MODE ←──── ESC ────── INSERT MODE         │
│  (navigate,       ─── i/a/o ──→  (type text)     │
│   delete,                                         │
│   copy/paste)     ─── : ──→ COMMAND MODE          │
│                              (save, quit,         │
│                               search/replace)     │
└────────────────────────────────────────────────────┘

You START in Normal mode. Press 'i' to type. Press ESC to stop typing.

# Create a practice file

STEP 1: You're in NORMAL mode. You CAN'T type yet.
         (This confuses everyone the first time — it's by design)

Essential Navigation (Normal Mode):

h = left     (or ← arrow)
j = down     (or ↓ arrow)
k = up       (or ↑ arrow)
l = right    (or → arrow)

But the REAL navigation (what pros actually use):
gg    = go to first line    → "jump to top of config file"
G     = go to last line     → "jump to end of log file"
5G    = go to line 5        → "error on line 5, go there"
0     = go to beginning of line
$     = go to end of line   → "append something at end of this line"
w     = jump forward one word  → "skip to next word quickly"
b     = jump backward one word
Ctrl+f = page down          → "scroll through large file"
Ctrl+b = page up

Ways to Enter Insert Mode:

i = insert before cursor      → Most common, "I want to type here"
a = insert after cursor       → "I want to type AFTER this character"
I = insert at beginning       → "I want to add something at line start"
A = insert at end of line     → "I want to append to this line"
o = open new line below       → "I want to add a new line after this"
O = open new line above       → "I want to add a new line before this"

Real use cases:
- Editing a config value? Position on the value, use 'cw' (change word)
- Adding a new config line? Go to nearby line, press 'o'

2.3 — "Editing Power — Delete, Copy, Paste, Undo" (10 min)

Hands-on (open vim /tmp/practice.txt):

DELETING (Normal mode):
x     = delete character under cursor   → "fix a typo (one char)"
dd    = delete entire line              → "remove this config line"
5dd   = delete 5 lines                  → "remove this whole block"
dw    = delete word                     → "remove just this word"
d$    = delete from cursor to end       → "erase the rest of this line"
d0    = delete from cursor to beginning → rarely used

WHEN TO USE: Editing config files — removing old entries, cleaning up
lines. "dd" is your most-used delete. "5dd" removes blocks.

UNDO / REDO:
u     = undo last change      → "oops, that was wrong, take it back"
Ctrl+r = redo (undo the undo) → "wait no, that change WAS correct"

WHEN TO USE: You just deleted the wrong line? Press 'u' immediately.
Vim has UNLIMITED undo — you can undo your way back to the original file.

COPY (yank) and PASTE:
yy    = copy (yank) current line    → "I need this line somewhere else"
5yy   = copy 5 lines               → "copy this whole block"
yw    = copy word                   → "just need this value"
p     = paste below current line    → "put it here"
P     = paste above current line

WHEN TO USE: Duplicating config blocks (copy a server block in nginx,
paste it, then modify the copy). Way faster than retyping.

CUT + PASTE (MOVE lines):
dd    = cuts the line (it's in the buffer)
p     = paste it somewhere else
# This is how you MOVE lines in vim
# Real use: reorder config entries, move a function definition

REPLACE:
r     = replace single character    → "change 80 to 90 (just the 8)"
R     = replace mode (overwrite)    → "overwrite this whole section"
cw    = change word (delete + insert) → "change 'nginx' to 'apache'"
cc    = change entire line          → "rewrite this whole line"

WHEN TO USE: "cw" is a DevOps favorite — position on a config value
(like a port number or hostname), press cw, type the new value. Done.

2.4 — "Search, Replace & Command Mode" (7 min)

Hands-on:

SEARCH (Normal mode):
/pattern    = search forward (press n for next, N for previous)
?pattern    = search backward

Example:
/cherry     → finds "cherry", press n to go to next match
?apple      → searches backward for "apple"
/error      → search for "error" in a log file (then n, n, n to scan)

WHEN TO USE: Opening a 5000-line log file? Type /ERROR to jump
straight to errors. Way faster than scrolling.

SEARCH AND REPLACE (Command mode):
:s/old/new/         = replace first occurrence on current line
:s/old/new/g        = replace ALL on current line
:%s/old/new/g       = replace ALL in entire file
:%s/old/new/gc      = replace ALL but ask for Confirmation each time

Real examples:
:%s/80/8080/gc      → change port 80 to 8080 (confirm each — careful!)
:%s/staging/production/g → switch environment in config
:%s/old-domain.com/new-domain.com/g → domain migration in config

WHEN TO USE: Bulk changes in config files. The "gc" (confirm) flag is
ESSENTIAL when you're not 100% sure what will match. In production,
ALWAYS use gc first to preview what will change.

USEFUL COMMANDS:
:set number         = show line numbers    → "error on line 42, let me see"
:set nonumber       = hide line numbers
:set paste          = paste mode           → USE THIS before pasting from clipboard
:set nopaste        = exit paste mode        (prevents auto-indent mess)
:syntax on          = syntax highlighting  → makes YAML/JSON/config readable
:w                  = save (don't quit)    → "save my work, keep editing"
:q                  = quit (fails if unsaved changes)
:q!                 = force quit WITHOUT saving → "I messed up, abandon everything"
:wq                 = save and quit        → "done editing, save and leave"
:x                  = same as :wq
ZZ                  = same as :wq (in normal mode, no colon needed)

WHEN TO USE :set paste:
When you copy a YAML/JSON snippet from your browser and paste into vim,
without :set paste, vim will auto-indent each line and create a
"staircase" effect. ALWAYS :set paste first, paste, then :set nopaste.

SPLIT WINDOWS:
:split filename     = horizontal split  → "compare two config files"
:vsplit filename    = vertical split    → "old config vs new config"
Ctrl+w, then arrow  = switch between splits
:q                  = close current split

WHEN TO USE: Comparing the old config with a new one side-by-side,
or editing a file while reading another as reference.

OPEN MULTIPLE FILES:
vim file1 file2     = open both
:n                  = next file
:prev               = previous file
:ls                 = list open buffers

3.1 — "What is systemd?" (5 min)

Theory:

systemd = the "init system" — PID 1 on modern Linux

Its job:
1. BOOTS the system (starts services in the right order)
2. MANAGES services (start, stop, restart, enable/disable)
3. TRACKS dependencies ("start nginx AFTER network is up")
4. MONITORS processes (restarts crashed services automatically)
5. LOGS everything (journald)

Before systemd: SysVinit (older — used /etc/init.d/ scripts)
Modern Linux (Ubuntu 16+, CentOS 7+, Debian 8+): all use systemd

Key terms:
- Unit     = anything systemd manages (service, timer, mount, etc.)
- Service  = a daemon/background process (nginx, ssh, docker)
- Target   = a group of units (like "multi-user mode" or "graphical mode")
- Enable   = start automatically on boot
- Disable  = don't start on boot (but can be started manually)

3.2 — "Managing Services" (12 min)

Hands-on:

# ┌─────────────────────────────────────────────────────────────┐
# │ COMMAND: systemctl status SERVICE                           │
# │ WHEN TO USE: First thing to check when troubleshooting      │
# │ REAL USE CASE:                                              │
# │   - "Is my web server running?"                             │
# │   - "Why is the app down?" → status shows error messages    │
# │   - Check PID, memory usage, recent logs all in one place   │
# │   - After a deployment: "did the service come back up?"     │
# └─────────────────────────────────────────────────────────────┘
systemctl status nginx
# Shows:
# - Active: active (running) ← GREEN = good
# - Active: failed ← RED = something went wrong
# - Main PID: 1234 (nginx)
# - Memory / CPU usage
# - Last 10 log lines (often shows the error!)

# ┌─────────────────────────────────────────────────────────────┐
# │ COMMANDS: start / stop / restart / reload                   │
# │ WHEN TO USE EACH:                                           │
# │                                                             │
# │ start   → Service is stopped, you want it running           │
# │   Real: "Deploy done, start the app"                        │
# │                                                             │
# │ stop    → You need the service down (maintenance, debug)    │
# │   Real: "Stop nginx before changing SSL certs"              │
# │                                                             │
# │ restart → Config change requires full restart, OR service   │
# │           is misbehaving and you want a fresh start         │
# │   Real: "Java app needs restart after deploy"               │
# │   WARNING: Causes brief downtime! Connections are dropped.  │
# │                                                             │
# │ reload  → Config changed but service supports hot-reload    │
# │   Real: "nginx config changed, reload without dropping      │
# │          existing connections" → zero downtime!             │
# │   NOTE: Not all services support reload.                    │
# └─────────────────────────────────────────────────────────────┘
sudo systemctl start nginx      # start it now
sudo systemctl stop nginx       # stop it now
sudo systemctl restart nginx    # stop + start (brief downtime)
sudo systemctl reload nginx     # re-read config without stopping (zero downtime!)

# Verify after each:
systemctl status nginx

# ┌─────────────────────────────────────────────────────────────┐
# │ COMMANDS: enable / disable                                  │
# │ WHEN TO USE:                                                │
# │                                                             │
# │ enable  → You want this service to survive reboots          │
# │   Real: "nginx should start automatically after server      │
# │          reboots (maintenance, crash recovery, auto-scaling)"│
# │                                                             │
# │ disable → Service should NOT start on boot                  │
# │   Real: "We decommissioned this service but haven't         │
# │          uninstalled it yet" or "testing only"              │
# │                                                             │
# │ IMPORTANT: enable/disable only affect BOOT behavior.        │
# │ enable does NOT start the service. disable does NOT stop it.│
# │ Use enable --now to do both.                                │
# └─────────────────────────────────────────────────────────────┘
sudo systemctl enable nginx     # start on boot
sudo systemctl disable nginx    # don't start on boot
sudo systemctl enable --now nginx  # enable AND start immediately

# ┌─────────────────────────────────────────────────────────────┐
# │ COMMAND: systemctl is-enabled / is-active                   │
# │ WHEN TO USE: Quick checks in scripts and monitoring         │
# │ REAL USE CASE:                                              │
# │   - Ansible playbooks check is-active before proceeding     │
# │   - Monitoring scripts alert if service is inactive         │
# │   - CI/CD pipelines verify service started after deploy     │
# └─────────────────────────────────────────────────────────────┘
systemctl is-enabled nginx    # "enabled" or "disabled"
systemctl is-active nginx     # "active" or "inactive"

# ┌─────────────────────────────────────────────────────────────┐
# │ COMMAND: systemctl list-units / --failed                    │
# │ WHEN TO USE: Get overview of all services on the machine    │
# │ REAL USE CASE:                                              │
# │   - First login to a new server: "what's running here?"     │
# │   - After reboot: "did everything come back up?"            │
# │   - Troubleshooting: "are there any failed services?"       │
# └─────────────────────────────────────────────────────────────┘
systemctl list-units --type=service --state=running
systemctl list-units --type=service --all
systemctl --failed
# If you see failed services, investigate with: journalctl -u servicename

# See what starts at boot:
systemctl list-unit-files --type=service | grep enabled

3.3 — "Reading Logs with journalctl" (8 min)

Theory:

journalctl = systemd's log viewer
- Replaces reading /var/log/syslog manually
- Can filter by service, time, priority
- Structured logging (JSON available)

Priority levels (from most to least severe):
0 = emerg    (system unusable)
1 = alert    (immediate action needed)
2 = crit     (critical)
3 = err      (errors)    ← Start investigating here
4 = warning  (warnings)  ← Watch these
5 = notice   (normal but significant)
6 = info     (informational)
7 = debug    (debug messages)

Hands-on:

# ┌─────────────────────────────────────────────────────────────┐
# │ COMMAND: journalctl -u SERVICE                              │
# │ WHEN TO USE: Check logs for a specific service              │
# │ REAL USE CASE:                                              │
# │   - "nginx won't start — what's the error?"                │
# │   - "App is crashing — what's in the logs?"                │
# │   - Post-mortem: "what happened at 3 AM?"                  │
# │   - After deployment: "are there errors in the new version?"│
# └─────────────────────────────────────────────────────────────┘
journalctl -u nginx
# -u = unit (service name)

# ┌─────────────────────────────────────────────────────────────┐
# │ COMMAND: journalctl -u SERVICE -f                           │
# │ WHEN TO USE: Watch logs in real-time (live tail)            │
# │ REAL USE CASE:                                              │
# │   - During deployment: watch for errors as new version starts│
# │   - Debugging: reproduce the bug while watching logs        │
# │   - Monitoring: "let me keep an eye on this service"        │
# │   - Like tail -f but with filtering powers                  │
# └─────────────────────────────────────────────────────────────┘
journalctl -u nginx -f
# Press Ctrl+C to stop

# ┌─────────────────────────────────────────────────────────────┐
# │ COMMAND: journalctl -u SERVICE -n 50                        │
# │ WHEN TO USE: See only the last N lines (not entire history) │
# │ REAL USE CASE: Quick glance at recent behavior without      │
# │   scrolling through thousands of old log lines              │
# └─────────────────────────────────────────────────────────────┘
journalctl -u nginx -n 50

# ┌─────────────────────────────────────────────────────────────┐
# │ COMMAND: journalctl --since "TIME"                          │
# │ WHEN TO USE: Investigate issues from a specific time period │
# │ REAL USE CASE:                                              │
# │   - "Users reported errors at 2 PM" → check logs from 2 PM │
# │   - "What happened since the last deploy?"                  │
# │   - Incident response: "show me the last hour of logs"      │
# └─────────────────────────────────────────────────────────────┘
journalctl -b                              # since last boot
journalctl --since "2024-01-01 10:00:00"   # specific timestamp
journalctl --since "1 hour ago"            # relative time
journalctl --since "today"                 # since midnight
journalctl --since "2024-01-01" --until "2024-01-02"  # range

# ┌─────────────────────────────────────────────────────────────┐
# │ COMMAND: journalctl -p err                                  │
# │ WHEN TO USE: Filter by severity (show only errors+)         │
# │ REAL USE CASE:                                              │
# │   - Morning check: "any errors overnight?"                  │
# │   - Hundreds of info logs but you only want errors          │
# │   - Combine with --since for focused investigation          │
# └─────────────────────────────────────────────────────────────┘
journalctl -p err
# Shows only priority 0-3 (emerg, alert, crit, err)

# THE POWER COMBO (use this in real incidents):
journalctl -u nginx -p err --since "1 hour ago"
# "Show me nginx errors from the last hour" — surgical precision

# ┌─────────────────────────────────────────────────────────────┐
# │ COMMAND: journalctl --disk-usage / --vacuum-*               │
# │ WHEN TO USE: Logs eating too much disk space                │
# │ REAL USE CASE:                                              │
# │   - "Disk is 95% full" → check if logs are the culprit     │
# │   - Maintenance: periodically clean old logs                │
# │   - Set up in cron for automatic cleanup                    │
# └─────────────────────────────────────────────────────────────┘
journalctl --disk-usage

# Clean old logs (keep only last 2 days)
sudo journalctl --vacuum-time=2d
# OR keep only 500MB
sudo journalctl --vacuum-size=500M

# ┌─────────────────────────────────────────────────────────────┐
# │ COMMAND: journalctl -o json-pretty                          │
# │ WHEN TO USE: Export logs for external systems               │
# │ REAL USE CASE:                                              │
# │   - Feeding logs to ELK Stack / Splunk / Loki              │
# │   - Parsing logs programmatically in scripts                │
# │   - Getting structured data with all metadata               │
# └─────────────────────────────────────────────────────────────┘
journalctl -u nginx -o json-pretty -n 5

3.4 — "Creating Your Own Service" (10 min)

Theory:

A unit file tells systemd:
- WHAT to run
- WHEN to run it (after what dependency)
- HOW to run it (user, restart policy, environment)
- WHERE to put the service file: /etc/systemd/system/

Unit file structure:
[Unit]        = metadata (description, dependencies)
[Service]     = how to run (command, user, restart)
[Install]     = when to enable (which target)

WHEN DO YOU CREATE CUSTOM SERVICES?
- Your company builds a custom application (Python/Node/Go/Java app)
- You need it to run as a daemon (background process)
- It should auto-restart on crash
- It should start on boot
- You want centralized logging (journalctl)

Real examples:
- A Node.js API server
- A Python data pipeline worker
- A Go microservice
- A custom monitoring agent
- A backup script that runs as a daemon

Hands-on:

# Step 1: Create a simple application
cat << 'EOF' > /tmp/myapp.sh
#!/bin/bash
while true; do
    echo "$(date): MyApp is running — PID $$" >> /tmp/myapp.log
    sleep 5
done
EOF
chmod +x /tmp/myapp.sh

# Step 2: Create the systemd service unit file
sudo vim /etc/systemd/system/myapp.service
[Unit]
Description=My Demo Application
After=network.target
# After= → "Don't start me until network is ready"
# Real use: Your app needs network to connect to a database
# Other common values: After=postgresql.service (start after DB)

[Service]
Type=simple
# Type=simple → The process in ExecStart IS the service (most common)
# Type=forking → The process forks into background (like Apache)
# Type=oneshot → Runs once and exits (like a migration script)

ExecStart=/tmp/myapp.sh
# What command to run. MUST be absolute path.

ExecStop=/bin/kill -SIGTERM $MAINPID
# How to stop it gracefully (optional — systemd does SIGTERM by default)

Restart=always
# Restart policy:
# always       → restart no matter how it exited (production apps)
# on-failure   → restart only if exit code != 0 (most common)
# no           → never auto-restart (one-shot tasks)
# Real use: "My app crashed at 3 AM, systemd restarted it in 3 seconds"

RestartSec=3
# Wait 3 seconds before restarting (prevents restart loops)

User=nobody
# Run as this user (NEVER run apps as root!)
# Real use: User=www-data for web apps, User=prometheus for monitoring

StandardOutput=journal
StandardError=journal
# Send stdout/stderr to journalctl (centralized logging)

[Install]
WantedBy=multi-user.target
# When this service is "enabled", add it to multi-user.target
# This means: start on boot (in non-GUI server mode)
# ┌─────────────────────────────────────────────────────────────┐
# │ COMMAND: systemctl daemon-reload                            │
# │ WHEN TO USE: After creating or modifying ANY unit file      │
# │ REAL USE CASE: You edited a .service file — systemd doesn't │
# │   know about it until you reload. ALWAYS run this.          │
# │   Forgetting this = "why isn't my change taking effect??"   │
# └─────────────────────────────────────────────────────────────┘
# Step 3: Tell systemd about the new service
sudo systemctl daemon-reload

# Step 4: Start and enable
sudo systemctl start myapp
sudo systemctl enable myapp

# Step 5: Verify
systemctl status myapp
# Should show: active (running)

# Check the logs
journalctl -u myapp -f
# You should see "MyApp is running" every 5 seconds

# Check the log file too
tail -f /tmp/myapp.log

# Step 6: Test auto-restart (THIS is the magic of systemd!)
# Simulate a crash — kill the process manually
pgrep -f myapp.sh
sudo kill $(pgrep -f myapp.sh)

# Wait 3 seconds (RestartSec=3), then check
sleep 4
systemctl status myapp
# It should be running again! systemd restarted it automatically.
# THIS is why we use systemd — your app self-heals from crashes!
# Without systemd: your app crashes at 3 AM, nobody notices until morning.
# With systemd: it restarts in 3 seconds, users barely notice.

# Step 7: Clean up
sudo systemctl stop myapp
sudo systemctl disable myapp
sudo rm /etc/systemd/system/myapp.service
sudo systemctl daemon-reload
rm /tmp/myapp.sh /tmp/myapp.log

Networking Interview Questions

Q1: How do you check which port a service is listening on?

# Best answer:
ss -tulnp | grep <service_name>
# OR
sudo lsof -i -P -n | grep LISTEN
# OR
sudo netstat -tulnp | grep <service_name>

Q2: A website is not loading. How do you troubleshoot?

# Step-by-step:
# 1. Is DNS resolving?
nslookup example.com
dig example.com

# 2. Can I reach the IP?
ping -c 3 <resolved-ip>

# 3. Is the port open?
nc -zv <ip> 80
nc -zv <ip> 443

# 4. What does the HTTP response say?
curl -vI https://example.com

# 5. Is there a firewall blocking?
sudo iptables -L -n
# Or on cloud: check Security Groups / NACLs

# 6. Is the service actually running?
systemctl status nginx
ss -tlnp | grep :80

Q3: What's the difference between TCP and UDP?

TCP:
- Connection-oriented (3-way handshake: SYN → SYN-ACK → ACK)
- Guaranteed delivery (retransmits lost packets)
- Ordered (packets arrive in sequence)
- Use: HTTP, SSH, FTP, database connections

UDP:
- Connectionless (fire and forget)
- No guarantee (packets may be lost)
- No ordering
- Use: DNS, video streaming, gaming, VoIP
- Faster but less reliable

Q4: How do you find which process is using a specific port?

# Port 80:
sudo lsof -i :80
sudo ss -tulnp | grep :80
sudo fuser 80/tcp
# The last one also gives you the option to kill it: fuser -k 80/tcp

Q5: How do you check the route packets take to reach a server?

traceroute google.com
# Shows each hop with latency
# * = no response (firewall)
# Increasing latency at a hop = congestion at that point

Q6: What's the difference between /etc/hosts and DNS?

/etc/hosts:
- Local file, checked FIRST
- Static entries (you manually add them)
- No network request needed
- Use: local overrides, dev environments, blocking domains

DNS:
- External server (/etc/resolv.conf has the server IPs)
- Dynamic (can change without you doing anything)
- Network request required
- Use: everything else (internet browsing, service discovery)

Order is defined in: /etc/nsswitch.conf (hosts: files dns)

Systemd Interview Questions

Q11: How do you check why a service failed to start?

# Step 1: Check status (shows error in output)
systemctl status nginx

# Step 2: Check detailed logs
journalctl -u nginx -n 50 --no-pager

# Step 3: Check for syntax errors in config
nginx -t   # for nginx specifically
# Each service usually has a config test command

# Step 4: Check if port is already in use
ss -tlnp | grep :80

Q12: What's the difference between systemctl restart and systemctl reload?

restart:
- Stops the service completely, then starts it again
- Brief downtime (connections are dropped)
- Use when: major config changes, version upgrades

reload:
- Tells the service to re-read its configuration
- Zero downtime (existing connections maintained)
- Use when: minor config changes (nginx reload = graceful)
- Not all services support reload

reload-or-restart:
- Tries reload first; if not supported, does restart

Q13: How do you make a service start on boot?

sudo systemctl enable nginx        # enables on boot
sudo systemctl enable --now nginx  # enables AND starts immediately

# Verify:
systemctl is-enabled nginx
# Check what target it's linked to:
ls -la /etc/systemd/system/multi-user.target.wants/ | grep nginx

Q14: How do you create a custom systemd service?

# 1. Create the unit file:
sudo vim /etc/systemd/system/myservice.service

# 2. Minimum viable unit file:
# [Unit]
# Description=My Service
# After=network.target
#
# [Service]
# ExecStart=/usr/bin/myapp
# Restart=always
#
# [Install]
# WantedBy=multi-user.target

# 3. Reload systemd:
sudo systemctl daemon-reload

# 4. Start and enable:
sudo systemctl enable --now myservice

Q15: How do you see all failed services and fix them?

# List failed:
systemctl --failed

# Investigate each:
journalctl -u <failed-service> -p err

# Reset failed state after fixing:
sudo systemctl reset-failed <service>

Scenario-Based Interview Questions

Q16: "Production server is slow. Walk me through your troubleshooting."

# 1. Overall system health
top        # or htop — check CPU, memory, load average
uptime     # load average vs CPU cores
free -h    # memory usage (is swap being used heavily?)
df -h      # disk full?

# 2. Network issues?
ss -s      # connection summary (too many connections?)
ss -tn state established | wc -l    # connection count

# 3. Which process is hogging resources?
ps aux --sort=-%cpu | head -5   # top CPU
ps aux --sort=-%mem | head -5   # top memory

# 4. IO bottleneck?
iostat 1 5    # disk I/O (if available)
cat /proc/diskstats

# 5. Check service health
systemctl status <your-service>
journalctl -u <your-service> --since "10 min ago" -p err

Q17: "Port 80 is already in use, nginx won't start."

# Find who's using port 80:
sudo lsof -i :80
sudo ss -tlnp | grep :80

# If it's Apache:
sudo systemctl stop apache2
sudo systemctl disable apache2

# Now start nginx:
sudo systemctl start nginx
systemctl status nginx

Q18: "How do you securely transfer files between servers?"

# Method 1: SCP (simple, SSH-based)
scp file.txt user@remote:/path/

# Method 2: rsync (better for large/many files, resumes)
rsync -avz -e ssh /local/path/ user@remote:/remote/path/
# -a = archive mode (preserves permissions)
# -v = verbose
# -z = compress during transfer

# Method 3: sftp (interactive FTP over SSH)
sftp user@remote

# All three use SSH encryption = secure
# NEVER use plain FTP (port 21) — unencrypted, passwords visible!

Q19: "What's the difference between kill, kill -9, and kill -HUP?"

kill (SIGTERM, signal 15):
- "Please shut down gracefully"
- Process can catch this, clean up, and exit
- ALWAYS try this first

kill -9 (SIGKILL, signal 9):
- "Die immediately, no questions"
- Process CANNOT catch or ignore this
- No cleanup — may corrupt data
- Last resort only

kill -HUP (SIGHUP, signal 1):
- "Reload your configuration"
- Many daemons (nginx, sshd) re-read config on HUP
- No downtime — process stays running

Q20: "A colleague left a vim session running. You see a .swp file. What do you do?"

# .swp file = vim swap file from an active or crashed session
ls -la .filename.swp

# Check if vim is still running:
ps aux | grep vim

# If process exists: ask the colleague or kill it
# If no process: vim crashed, recover the file:
vim filename
# Vim will ask: [R]ecover, [D]elete, [Q]uit, [A]bort
# Press R to recover, save it, then delete the .swp:
rm .filename.swp

Tips for Delivery

  • Live troubleshoot: Break nginx on purpose (bad config), show students how to find the error with systemctl status + journalctl

  • Network mystery: Stop nginx, ask students to figure out why "curl localhost" fails — teach the troubleshooting mindset
  • Two terminals: One for running commands, one with journalctl -f or ss -tn live
