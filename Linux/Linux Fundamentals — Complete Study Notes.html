1. Infrastructure Evolution & The Cloud

The transition from physical data centers to modern cloud-native architectures solved several operational challenges:

+------------------+      +-------------------+      +--------------------+      +--------------------+
|   Bare Metal     |      |  Virtualization   |      |  Containerization  |      |   Public Cloud     |
|   (1990s-2000s)  | ---> |   (Early 2000s)   | ---> |     (2013+)        | ---> |     (Modern)       |
| 1 App per Server |      | Hypervisor + VMs  |      | Shared OS Kernel   |      | Pay-as-you-go IaaS |
+------------------+      +-------------------+      +--------------------+      +--------------------+
  • Bare Metal (Physical Machines): High capital expense (CapEx), single-application setups per host, manual OS patching, hardware redundancy requirements (dual power supplies, multi-homed NICs), and hardware failover overhead.
  • Virtualization: Introduction of hypervisors allowing multiple Guest OS instances on a single Host OS. Improved compute utilization, though each VM carried guest OS storage/RAM overhead.
  • Containerization: Process-level isolation sharing the host Linux kernel. Stripped away bloated OS suites, reducing baseline footprints from gigabytes down to megabytes (e.g., Alpine Linux at ~5 MB).
  • Public Cloud: Fully abstracted, on-demand compute infrastructure following a pay-as-you-go model.

Quick Reference

  • Bare Metal (Physical Machines): High capital expense (CapEx), single-application setups per host
  • Virtualization: Introduction of hypervisors allowing multiple Guest OS instances on a single Host OS
  • Containerization: Process-level isolation sharing the host Linux kernel
  • Public Cloud: Fully abstracted, on-demand compute infrastructure following a pay-as-you-go model

3. Kernel vs. Distributions (Distros)

In this section:

  • Common Distributions & Package Managers

Core Concept: Linux is strictly the kernel, not the complete operating system.

  • The Kernel (The Engine): The low-level interface that directly manages hardware, CPU, memory, and devices. Written primarily in C (with modern additions in Rust).
  • The Distribution (The Complete Car): A packaged bundle containing the Linux kernel alongside:
    • System initialization managers (e.g., systemd).
    • Native package managers.
    • Core GNU utilities (bash, grep, coreutils).
    • Security policies and firewall suites (iptables, firewalld).

Under the hood, all Linux distributions share the same kernel architecture. Approximately 95% of standard commands and APIs remain consistent across all distributions.

4. Core Linux Philosophies

In this section:

  • 1. The Unix Philosophy
  • 2. "Everything is a File"

1. The Unix Philosophy

  1. Single-Purpose Tools: Write programs that do one specific task exceptionally well.
  2. Standard Interfaces & Chaining: Write programs to work together. Send the standard output (stdout) of one utility as the standard input (stdin) of another using pipes (|).

Practical Chaining Examples

# 1. Inspect the top 5 CPU-consuming processes (strip columns, sort descending, limit output)
ps aux | awk '{print $1, $3}' | sort -k2 -rn | head -n 5

# 2. Count internal server error (HTTP 500) occurrences in an Nginx access log
grep " 500 " /var/log/nginx/access.log | wc -l

2. "Everything is a File"

In Linux, devices, running process metadata, hardware metrics, and network sockets are exposed as filesystem paths:

  • Hardware block storage: /dev/sda
  • CPU metadata & core topology: /proc/cpuinfo
  • Process memory metrics: /proc/meminfo
  • Standard system sink/discard: /dev/null

Quick Reference

  • ps aux | awk '{print $1, $3}' | sort -k2 -rn | head -n 5 — Inspect the top 5 CPU-consuming processes (strip columns, sort descending, limit output)
  • grep " 500 " /var/log/nginx/access.log | wc -l — Count internal server error (HTTP 500) occurrences in an Nginx access log
  • Single-Purpose Tools: Write programs that do one specific task exceptionally well
  • /dev/sda — Hardware block storage; /proc/cpuinfo — CPU metadata & core topology; /dev/null — Standard system sink/discard

5. Operating System Internals & Memory Spaces

In this section:

  • User Space vs. Kernel Space
  • 5 Core Kernel Responsibilities

Memory (RAM) is split by the kernel into two strict address spaces to safeguard system security and stability:

+------------------------------------------------------------------+
|                           Physical RAM                           |
+---------------------------------+--------------------------------+
|          Kernel Space           |           User Space           |
|  - Full privileges              |  - Restricted privileges       |
|  - Direct hardware access       |  - Runs apps (Nginx, Python)   |
|  - Crash = System Panic         |  - Crash = Isolated process dies|
+---------------------------------+--------------------------------+
                  ^                               |
                  |--- System Call (Syscall) <----+

User Space vs. Kernel Space

  • User Space: Sandboxed region where regular user applications (Nginx, databases, custom scripts) execute. Applications have no direct hardware execution rights. If an application encounters a fatal fault, only that isolated process terminates.
  • Kernel Space: Highly privileged memory territory reserved strictly for the kernel and core device drivers. It holds complete control over all hardware execution. A fatal error or panic here halts the entire operating system.

5 Core Kernel Responsibilities

  1. Process Management: Manages context switching across CPU cores, scheduling execution time rapidly so processes execute concurrently.
  2. Memory Management: Maps isolated virtual memory addresses to physical RAM blocks, managing page tables and caching algorithms (LRU).
  3. Filesystem Management: Translates high-level read/write commands into physical disk block operations.
  4. Device Management: Operates device drivers communicating with peripheral hardware (NICs, block storage, displays).
  5. Network Stack Management: Manages packet serialization, routing tables, TCP/UDP sockets, and network interfaces.

Quick Reference

  • User Space: Sandboxed region where regular user applications (Nginx, databases, custom scripts) execute
  • Kernel Space: Highly privileged memory territory reserved strictly for the kernel and core device drivers
  • Process Management: Manages context switching across CPU cores
  • Memory Management: Maps isolated virtual memory addresses to physical RAM blocks
  • Network Stack Management: Manages packet serialization, routing tables, TCP/UDP sockets, and network interfaces

6. System Calls (Syscalls)

In this section:

  • Common System Calls

A System Call is the programmatic gate allowing a user-space application to request a privileged action from the kernel.

[ User Application: Python / Nginx ]
               │
               ▼
   [ Language Runtime API: open() ]
               │
               ▼
   [ System Call Interface: sys_open ]
═══════════════════════════════════════════ (User / Kernel Space Boundary)
               │
               ▼
      [ Linux Kernel Core ]
               │
               ▼
       [ Hardware / Disk ]

Common System Calls

  • Filesystem: open(), read(), write(), close()
  • Process Lifecycle: fork() (duplicate existing process), execve() (execute new binary), wait()
  • Memory Allocation: brk(), mmap() (map virtual memory pages)
  • Networking: socket(), bind(), connect(), sendto(), recvfrom()

Diagnostic Tip: Use strace to trace the real-time system calls generated by any Linux binary:

  • fork() — duplicate existing process; execve() — execute new binary

7. Linux Filesystem Hierarchy

In this section:

  • Virtual Filesystems (/proc)

The Linux directory structure complies with the Filesystem Hierarchy Standard (FHS), branching from the single root directory /:

/
├── bin/          -> Essential user command binaries (ls, bash, cp)
├── sbin/         -> System administration binaries (fdisk, reboot, ip)
├── etc/          -> Host-specific system-wide configuration files (etc/hosts, etc/fstab)
├── home/         -> Standard user home directories (/home/username)
├── root/         -> Home directory for the root superuser
├── var/          -> Variable data files
│   └── log/      -> Persistent system and application logs
├── tmp/          -> Temporary files (cleared across reboots)
├── usr/          -> Multi-user read-only utilities, libraries, and binaries
│   └── bin/      -> Non-essential general user binaries
├── lib/          -> Shared system libraries required for core binaries and kernel modules
├── dev/          -> Special device nodes representing physical/virtual hardware (/dev/sda, /dev/null)
├── proc/         -> Virtual pseudo-filesystem exposing real-time kernel & process state
├── opt/          -> Optional third-party add-on application software packages
├── mnt/          -> Temporarily mounted external filesystems
└── boot/         -> Boot loader files, initramfs, and kernel vmlinuz images

Virtual Filesystems (/proc)

The /proc directory is a virtual filesystem generated in memory on the fly:

  • /proc/cpuinfo: Hardware CPU details, model specifications, core counts.
  • /proc/meminfo: Real-time system memory usage, buffers, and swap status.
  • /proc/loadavg: System load averages over 1, 5, and 15-minute intervals.
  • /proc/<PID>/: Contains the process state, open file descriptors, and runtime metrics for a specific Process ID.

Quick Reference

  • /proc/cpuinfo: Hardware CPU details, model specifications, core counts
  • /proc/meminfo: Real-time system memory usage, buffers, and swap status
  • /proc/loadavg: System load averages over 1, 5, and 15-minute intervals
  • /proc/<PID>/: Contains the process state, open file descriptors, and runtime metrics for a specific Process ID

DNS Resolution Lifecycle

When querying a domain like www.google.com. in a browser or terminal, the resolution follows these steps:

  1. Local System Cache: Checks local browser cache, OS resolver cache, and system DNS client.
  2. Local Static Hostfile: Reads /etc/hosts for hardcoded static IP-to-hostname mappings.
  3. Configured DNS Resolver: If unresolved, queries upstream recursive resolvers (configured in /etc/resolv.conf, e.g., Cloudflare 1.1.1.1 or Google 8.8.8.8).
  4. Root Name Servers (.): Directs query to the root level servers.
  5. Top-Level Domain (TLD) Servers (.com): Identifies authoritative servers for the TLD.
  6. Authoritative Name Servers (google.com): Looks up the specific host record (www) and returns the target A/AAAA IP address to the resolver.
  7. Client Connect & Cache: Resolver caches the record based on TTL and returns the IP to the client.

Shell vs. Bash Scripting

Shell (Interpreter): The generic command-line interface program that reads commands, translates them into system calls, and passes them to the kernel. Common shells include sh, bash, zsh, ksh, and fish.

Bash (Bourne Again Shell): An enhanced, POSIX-compliant implementation of the original Bourne shell (sh). It is the default shell across most enterprise Linux distributions.

Distinction:

  • Shell Scripting: Generic term for automating tasks across any compatible shell environment.
  • Bash Scripting: Scripts explicitly using the Bash interpreter (specified via #!/usr/bin/env bash), taking advantage of Bash-specific features like extended regular expressions, indexed arrays, and advanced parameter expansion.

Quick Reference

  • Local System Cache: Checks local browser cache, OS resolver cache, and system DNS client
  • Local Static Hostfile: Reads /etc/hosts for hardcoded static IP-to-hostname mappings
  • Configured DNS Resolver: queries upstream recursive resolvers (configured in /etc/resolv.conf)
  • Shell (Interpreter): The generic command-line interface program that reads commands, translates them into system calls, and passes them to the kernel
  • Bash (Bourne Again Shell): An enhanced, POSIX-compliant implementation of the original Bourne shell (sh)

4. Standard I/O Streams, Descriptors & Redirection

In this section:

  • The Null Device (/dev/null)

Every process started in a Linux environment is automatically assigned three standard I/O file descriptors:

[ Input Device: Keyboard ] ────> 0 (stdin)
                                    │
                                    ▼
                             [ Linux Process ]
                                    │
            ┌───────────────────────┴───────────────────────┐
            ▼                                               ▼
   1 (stdout: Normal Output)                      2 (stderr: Errors/Faults)
            │                                               │
            ▼                                               ▼
    [ Terminal Display ]                            [ Terminal Display ]
  • Standard Input (stdin, File Descriptor 0): Default input stream (interactive keyboard/pipe).
  • Standard Output (stdout, File Descriptor 1): Default destination for standard informational output.
  • Standard Error (stderr, File Descriptor 2): Dedicated stream for error notifications, diagnostic messages, and trace faults.

The Null Device (/dev/null)

/dev/null is a special character pseudo-device known as the "bit bucket" or "black hole". Any data written to it is discarded immediately, while reading from it returns an EOF (End of File).

Quick Reference

  • Standard Input (stdin, File Descriptor 0): Default input stream (interactive keyboard/pipe)
  • Standard Output (stdout, File Descriptor 1): Default destination for standard informational output
  • Standard Error (stderr, File Descriptor 2): Dedicated stream for error notifications, diagnostic messages, and trace faults
  • /dev/null — the "bit bucket" or "black hole"; any data written to it is discarded immediately

2. The Linux Security Architecture: UGO Model

Every file and directory in Linux enforces access control across three entity scopes:

  • User (u): The individual owner account that created the file (or was assigned via chown). Possesses primary discretionary control.
  • Group (g): A defined collection of user accounts sharing identical group permissions on the file. Eliminates the need to configure access per individual account.
  • Others (o): Any authenticated system process or user that is neither the file owner nor a member of the file's assigned group ("the rest of the world").

3. Permission Anatomy & Evaluation

In this section:

  • Permission Types: Files vs. Directories
  • Octal / Numeric Representation
  • Deconstructing ls -l Output

Permission Types: Files vs. Directories

Permissions operate differently depending on whether the target inode is a regular file or a directory:

  • Read (r):
    • On a Regular File: View/read raw file contents (cat, less).
    • On a Directory: List directory contents / entries (ls).
  • Write (w):
    • On a Regular File: Modify, append, or truncate file content.
    • On a Directory: Create, rename, or delete files inside.
  • Execute (x):
    • On a Regular File: Execute file as binary or shell script.
    • On a Directory: Traverse / enter directory (cd, search path).

Directory Traverse Requirement: A user must have execute (x) permissions on a directory to navigate into it or access its child items, even if they have read (r) access to files inside it.

Octal / Numeric Representation

Permissions are evaluated using 3-bit binary flags, converted into single-digit octal values (0 through 7):

  • Read (r) = 4
  • Write (w) = 2
  • Execute (x) = 1
  • Total Available Weight = 4 + 2 + 1 = 7
OctalSymbolicMeaning
0---No access whatsoever
1--xExecute only
2-w-Write only
3-wxWrite and Execute
4r--Read only
5r-xRead and Execute
6rw-Read and Write
7rwxFull Read, Write, and Execute

Deconstructing ls -l Output

An output like -rw-r--r-- 1 root root 1820 Sep 18 10:00 /etc/passwd breaks down into:

  • Position 1: Inode type indicator (- for regular file, d for directory, l for symbolic link, c for character device, b for block device).
  • Positions 2-4: Owner / User permissions (rw- = 6).
  • Positions 5-7: Group permissions (r-- = 4).
  • Positions 8-10: Others / World permissions (r-- = 4).
  • Remaining fields: Link count, User owner (root), Group owner (root), File size, Timestamp, Target path.

Quick Reference

  • Read (r) = 4; Write (w) = 2; Execute (x) = 1
  • Directory Traverse Requirement: A user must have execute (x) permissions on a directory to navigate into it or access its child items
  • Position 1: Inode type indicator (- for regular file, d for directory, l for symbolic link)
  • Positions 2-4: Owner / User permissions (rw- = 6)

4. Modifying Permissions (chmod)

In this section:

  • Numeric / Octal Mode
  • Symbolic Mode
  • Standard Production Permission Templates

The chmod (change mode) command modifies permission bits using either octal or symbolic syntax.

Numeric / Octal Mode

Overwrites the absolute permission state for all three scopes simultaneously:

chmod 755 deployment_script.sh
chmod 644 /etc/nginx/nginx.conf
chmod 600 ~/.ssh/id_rsa

Symbolic Mode

Applies targeted modifications using identity and arithmetic operators:

  • Identities: u (User), g (Group), o (Others), a (All: u+g+o)
  • Operators: + (Add), - (Remove), = (Set explicitly)
  • Actions: r, w, x

Examples:

# Add execute permission for all entities
chmod +x application.sh

# Add write permission strictly to the file owner
chmod u+w config.json

# Strip read rights completely from others
chmod o-r sensitive_data.txt

# Explicitly set read-only for group and others
chmod go=r index.html

# Apply permissions recursively down a directory tree
chmod -R 750 /var/www/internal

6. Special Permission Bits: SUID & Sticky Bit

In this section:

  • 1. Set UID (SUID) — Octal Weight: 4
  • 2. Sticky Bit — Octal Weight: 1

1. Set UID (SUID) — Octal Weight: 4

  • Function: When an executable with the SUID bit is launched, it runs with the privileges of the file's owner, rather than the user executing it.
  • Visual Representation: Displayed as an s in place of the owner execute bit (e.g., -rwsr-xr-x).
  • Classic Example: /usr/bin/passwd. Regular users must write to /etc/shadow to update passwords, but cannot read or edit it directly. The SUID flag runs passwd as root.
chmod u+s /usr/local/bin/custom_tool
# (or) chmod 4755 /usr/local/bin/custom_tool

2. Sticky Bit — Octal Weight: 1

  • Function: Enforced on directories. While multiple users may have write access to create files within the directory, a user can only delete or rename files they personally own.
  • Visual Representation: Displayed as a t in place of the others execute bit (e.g., drwxrwxrwt).
  • Classic Example: /tmp. A shared scratchpad where any user can generate files, but users cannot delete or overwrite each other's temporary data.
chmod +t /shared_scratch/
# (or) chmod 1777 /shared_scratch/

Quick Reference

  • Set UID (SUID): it runs with the privileges of the file's owner, rather than the user executing it
  • chmod u+s /usr/local/bin/custom_tool — SUID (or chmod 4755 /usr/local/bin/custom_tool)
  • Sticky Bit: a user can only delete or rename files they personally own
  • chmod +t /shared_scratch/ — Sticky Bit (or chmod 1777 /shared_scratch/)

7. Users, Groups & Account Categories

In this section:

  • Account Classes & UID/GID Allocations
  • The Superuser (root) & UID 0 Invariant

Account Classes & UID/GID Allocations

  • Superuser (root): UID/GID 0. Unrestricted kernel capabilities; hardcoded administrative account.
  • System / Service Accounts: UID/GID 1–999 (Debian/Ubuntu) or 1–499 (RHEL/CentOS). Dedicated bot accounts (nginx, postgres, systemd-resolve). No interactive login shells (/usr/sbin/nologin).
  • Regular User Accounts: UID/GID 1000–60000+. Human operators and interactive automation pipelines. Provided standard interactive shells (/bin/bash, /bin/zsh).

The Service Account Paradigm: Applications must never run under personal human user accounts. If a human engineer departs the organization and their account is purged, services tied to their identity crash. Service accounts provide isolated, application-specific lifecycles.

The Superuser (root) & UID 0 Invariant

  • The Linux kernel evaluates the numeric value UID == 0, not the string "root".
  • If an account is renamed from "root" to "admin" while retaining UID 0, the kernel continues to grant it complete superuser privileges.
  • UID 0 bypasses standard DAC file permission checks, can signal/terminate any running process, binds to privileged network ports (< 1024), and manages kernel modules.
  • Direct root SSH login (PermitRootLogin no in /etc/ssh/sshd_config) should be disabled across production systems in favor of least-privilege sudo access.

Quick Reference

  • Superuser (root): UID/GID 0. Unrestricted kernel capabilities
  • System / Service Accounts: UID/GID 1–999 (Debian/Ubuntu) or 1–499 (RHEL/CentOS)
  • Regular User Accounts: UID/GID 1000–60000+
  • The Linux kernel evaluates the numeric value UID == 0, not the string "root"
  • PermitRootLogin no in /etc/ssh/sshd_config — Direct root SSH login should be disabled across production systems

2. Hands-On: Permissions & Inode Semantics

In this section:

  • Default Directory vs. File Modes

Default Directory vs. File Modes

  • Regular Files: Default to non-executable modes upon creation (-rw-r--r-- / 644).
  • Directories: Require the execute bit (d rwxr-xr-x / 755) to enable directory entry and traversal.

The Directory Execute (x) Gotcha

  • Symptom: Recursively stripping execution permissions on directories (e.g., chmod -R 644 webdir) prevents non-root users from accessing the folder (cd webdir fails with Permission denied).
  • Core Rule:
    • Files: r allows viewing content; w allows modifying content; x allows execution as a binary or script.
    • Directories: r allows listing file names inside; w allows creating/deleting entries; x allows entering (cd) and accessing file metadata within the directory.

Modifying Permissions (chmod)

  • Symbolic Mode: Granular delta operations:
    chmod +x script.sh       # Add execute permissions to user, group, and others
chmod o-x script.sh       # Strip execute permissions from others
  • Octal / Numeric Mode: Absolute permission masks:
    chmod 755 script.sh      # rwxr-xr-x (standard executable)
chmod 644 public.txt     # rw-r--r-- (standard non-executable file)
chmod 600 secret.txt     # rw------- (owner read/write only)

    ⚠️ Warning: Using chmod 777 (rwxrwxrwx) introduces severe security vulnerabilities and is an administrative anti-pattern.

6. Theory: Introduction to Linux Process Management

In this section:

  • Process Definition
  • Process Control Block (PCB)
  • Context Switching Mechanics
  • Process Table Limits

Process Definition

  • A process is an instance of a program in active execution.
  • An inactive executable stored on disk is static; once loaded into memory by the kernel, it becomes a dynamic process. Multiple isolated running processes can originate from the exact same disk binary (such as multiple concurrent bash sessions).

Process Control Block (PCB)

The Linux kernel tracks every process using a dedicated in-memory data structure called the Process Control Block (implemented via struct task_struct), containing:

  • Identifiers: Process ID (PID) and Parent Process ID (PPID).
  • Execution State: Running (TASK_RUNNING), Interruptible Sleep (TASK_INTERRUPTIBLE), Uninterruptible Sleep (TASK_UNINTERRUPTIBLE), Stopped (TASK_STOPPED), or Zombie (EXIT_ZOMBIE).
  • Security & Credentials: Effective UID, Real UID, GID sets.
  • CPU Scheduling: Priority, nice value, real-time counters, and saved CPU registers (Program Counter, Stack Pointer).
  • Virtual Memory: Memory descriptors, page tables, code, data, BSS, stack, and heap boundaries.
  • File Descriptors: Pointer table referencing open files, sockets, and standard streams (stdin, stdout, stderr).

Context Switching Mechanics

During preemptive multitasking, CPU cores switch rapidly between tasks:

  1. An interrupt or system call triggers a context switch.
  2. The kernel halts the current process and serializes its register state into its PCB.
  3. The kernel's scheduler selects the next process to execute.
  4. The register states and memory mapping from the destination process's PCB are restored to the CPU hardware.

Process Table Limits

  • All active PCBs reside inside the kernel's process table.
  • The maximum PID boundary is configured globally in /proc/sys/kernel/pid_max.
  • If system PIDs or process table slots are exhausted (e.g., during a fork bomb), the kernel cannot create new processes or fork threads until existing tasks terminate.

Quick Reference

  • Process: an instance of a program in active execution
  • Process Control Block: a dedicated in-memory data structure (implemented via struct task_struct) the kernel uses to track every process
  • Context Switching: the kernel halts the current process and serializes its register state into its PCB
  • /proc/sys/kernel/pid_max — The maximum PID boundary is configured globally

2. Process Creation: The Fork-Exec Pattern

Processes are never created from scratch (except the initial init / PID 1 process spawned by the kernel at boot). All other processes follow the fork-exec model:

fork() System Call:

  • Duplicates the calling process.
  • Clones the parent's PCB, open file descriptors, variables, and memory state into a child process.
  • Returns 0 to the child process and returns the child's PID to the parent process.

exec() System Call (e.g., execve):

  • Replaces the cloned memory space, stack, and instructions with the target executable (e.g., running ls inside a shell).
  • Retains the PID assigned during fork().

exit() & wait():

  • When a child finishes, it calls exit(), returning an exit status (stored in the process table).
  • The parent must call wait() or waitpid() to read the exit code and release the child's PCB entry.
  • In interactive Bash, the exit status of the last executed command is retrieved using $? (0 = success, non-zero = error).

4. Linux Signals

Signals are asynchronous kernel interrupts sent to a process.

  • SIGTERM (Signal 15): Polite termination request. The application intercepts it, closes network sockets, flushes database write buffers, removes temporary files, and exits cleanly.
  • SIGKILL (Signal 9): Unconditional immediate kill performed directly by the kernel. Cannot be caught, blocked, or ignored. Can cause data corruption if the process was midway through disk/DB writes.
  • SIGHUP (Signal 1): Hangup signal. Often used by daemons (e.g., Nginx) to reload configuration files on the fly without dropping active connections or restarting the daemon.
  • SIGINT (Signal 2): Terminal interrupt generated via Ctrl + C. Defaults to terminating foreground processes, but can be trapped/handled by code.
  • SIGSTOP (Signal 19): Unconditionally pauses/freezes the process (similar to Ctrl + Z). Resumed via SIGCONT (Signal 18) or job control (fg/bg).
  • Special Case (PID 1): Kernel protects PID 1 (init/systemd); it ignores unhandled signals, including kill -9 1.

1. The Init System (PID 1 / systemd)

Origin: Unlike standard processes, PID 1 is not created via the fork() + exec() sequence. At boot time, the bootloader (GRUB) hands control over to the Linux kernel, which initializes system memory and launches the initial binary (/sbin/init, commonly symlinked to systemd).

Root of the Process Tree: Every running user and daemon process on the host is a direct or indirect descendant of PID 1.

Immunity to Signals:

  • Running kill -9 1 or sudo kill -15 1 fails (or triggers an intentional kernel panic/reboot). The kernel explicitly blocks unhandled signals directed at PID 1.

Core Responsibilities:

  • Service Life Cycle: Manages services, targets, mounts, and sockets via unit files and control tooling (systemctl start|stop|restart|reload <unit>).
  • Orphan Adoption & Zombie Reaping: Automatically takes custody of orphaned child processes and calls wait() when they terminate to remove their records from the process table.

Containers & PID 1 Pitfall:

  • Docker containers run the command specified in ENTRYPOINT/CMD as PID 1 (e.g., python main.py).
  • Because typical runtimes do not implement signal forwarding or child-reaping loops, sending docker stop (SIGTERM) can result in hung containers or zombie buildup.
  • Remedy: Integrate lightweight init binaries such as tini or dumb-init (or invoke Docker with --init).

Metric Header Breakdown (top)

  • Uptime & Load Average: Evaluated over 1, 5, and 15-minute windows:

$$\text{Capacity Threshold} = 1.0 \times \text{Total CPU Cores}$$

  • A load average of 4.0 on a 4-core machine indicates 100% saturation.
  • A load average exceeding core capacity (e.g., 8.0 on 4 cores) signals that runnable processes are actively queuing for CPU time.

  • Priority Metrics:

    • NI: Configurable nice value ranging from -20 (highest priority, root-only) to +19 (lowest priority).

The Core Prerequisites for Network Communication

Every host on an IP-based network relies on five fundamental configuration parameters:

  1. IP Address: Unique network identifier assigned to an interface.
  2. Subnet Mask / CIDR: Delineates the local network segment from foreign networks.
  3. Default Gateway: Next-hop router IP used when destinations fall outside the local subnet.
  4. DNS Server: Resolves human-readable domain names into target IP addresses.
  5. MAC Address: Unique 48-bit hardware identifier burned into the Network Interface Card (NIC).

Layer 2 (Data Link) vs. Layer 3 (Network)

+-------------------------------------+-------------------------------------+
|          MAC Address (L2)           |           IP Address (L3)           |
+-------------------------------------+-------------------------------------+

Address Resolution Protocol (ARP): Translates known Layer 3 IPv4 addresses into corresponding Layer 2 MAC addresses within the local broadcast domain.

Default Gateway Routing Logic

When a process initiates an outbound network packet:

                          Source Host generates Packet
                                       │
                                       ▼
                    Is Destination within Local Subnet?
                      (Evaluated via Subnet Mask)
                                  /         \
                             YES /           \ NO
                                ▼             ▼
                     Send directly to Host   Send to Default Gateway
                     via Local L2 ARP        (Next-hop Router IP)
                                                      │
                                                      ▼
                                             Gateway routes packet
                                             toward External Network

If a host can ping other nodes in the same local subnet (e.g., 192.168.1.50 pinging 192.168.1.60), but cannot reach internet hosts (e.g., 8.8.8.8):

  • Triage: The default gateway configuration (ip route) is missing, unreachable, or failing to perform outbound Network Address Translation (NAT).

Container Bridge Routing (docker0): Docker creates a virtual software bridge (docker0). Container network namespaces point their default gateway to docker0's IP (typically 172.17.0.1), which forwards packets to the physical host interface via iptables NAT.

Step-by-Step DNS Resolution Architecture

When a client queries a fully qualified domain name (FQDN) like docs.google.com:

Client Query: docs.google.com
   │
   ├─► 1. Browser & OS Cache  (Cached record found? ──► Return IP)
   │
   ├─► 2. /etc/hosts          (Static mapping found? ──► Return IP)
   │
   └─► 3. Local DNS Resolver  (/etc/resolv.conf, e.g., 8.8.8.8 or AWS 10.0.0.2)
         │
         ▼ (Iterative lookup if cache misses)
       4. Root Nameserver (`.`) ──────────────► Directs to TLD Nameserver
         │
         ▼
       5. Top-Level Domain (TLD) (`.com`) ──► Directs to Authoritative Nameserver
         │
         ▼
       6. Authoritative Nameserver (google.com) ──► Returns A/AAAA Record (IP)
         │
         ▼
       Response returned to Client & stored in local DNS cache based on TTL

/etc/resolv.conf: Stores local nameserver addresses queried by standard library resolvers:

nameserver 8.8.8.8
nameserver 1.1.1.1

AWS VPC DNS Allocation: In AWS VPC subnets, the VPC-provided DNS server (AmazonProvidedDNS) is always located at the base network CIDR block offset by +2 (e.g., in a 10.0.0.0/16 network, the VPC DNS address is 10.0.0.2; the default VPC router gateway is 10.0.0.1).

Time-to-Live (TTL) & Propagation: DNS records specify a TTL in seconds. Upstream recursive caches discard records only after this countdown expires, governing the duration of global DNS propagation during changes.

Subnet Mask & CIDR

  • Separates the Network ID from the Host ID.
  • Determines whether a destination IP is local (communicated via Ethernet/NIC) or remote (routed via the default Gateway).
  • Common CIDR blocks: /24 gives $2^{(32 - 24)} = 256$ IPs; /16 gives $2^{(32 - 16)} = 65,536$ IPs.

Ports & Sockets

  • Analogy: IP is the building address; port is the flat number.
  • Standard ports: 22 (SSH), 80 (HTTP), 443 (HTTPS), 3306 (MySQL), 5432 (PostgreSQL).
  • Port states: LISTEN, ESTABLISHED, TIME_WAIT, CLOSE_WAIT, SYN_SENT.

DNS Resolution Flow in Linux

  1. /etc/hosts (static local mappings; checked first).
  2. /etc/resolv.conf (configured local/upstream nameserver, e.g., systemd-resolved at 127.0.0.53).
  3. Upstream recursive resolver / custom DNS (e.g., Pi-hole, Google 8.8.8.8, Cloudflare 1.1.1.1).
  4. Root servers (.) $\rightarrow$ TLD servers (.com) $\rightarrow$ Authoritative nameservers.

DNS Record Types

A (IPv4), AAAA (IPv6), CNAME (canonical alias), MX (mail exchange), NS (nameserver delegation), TXT (domain verification / ACME challenges).

HTTP Headers

Metadata sent alongside HTTP requests/responses (e.g., Content-Type: application/json, authorization tokens, cache control).

Troubleshooting Workflow (Rule of Thumb)

Issue: Cannot reach service/machine
 ├── Step 1: ping <server_ip>
 │     ├── FAILS: Network/Routing issue
 │     │     └── Check default gateway (ip route show), trace hops (traceroute), check local link (ip link show).
 │     └── SUCCEEDS: Host is reachable, move to Step 2.
 └── Step 2: nc -vz <server_ip> <port>
       ├── FAILS: Port unreachable
       │     └── Check if service is running (ss -tulnp / systemctl status),
       │         or check firewalls (UFW, firewalld, Security Groups / iptables).
       └── SUCCEEDS: Port is open
             └── Issue lies in application logic, HTTP error codes (curl -v), or authorization.
